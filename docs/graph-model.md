# Graph Model: the `recommendations` Movie Dataset

This documents the property-graph model of the public `recommendations` database
(`neo4j+s://demo.neo4jlabs.com`), compiled from the
[official dataset repository](https://github.com/neo4j-graph-examples/recommendations)
and its guide. Run `uv run python scripts/discover_schema.py --write` against the live
server to append a freshly introspected snapshot below and confirm these details.

## The Model

```
                    ┌─────────┐
                    │  Genre  │  {name}
                    └────▲────┘
                         │ IN_GENRE
┌──────────────┐    ┌────┴────┐    ┌──────────┐
│    Person    │    │  Movie  │◄───┤   User   │
│ Actor/       │    │         │    │  {name}  │
│ Director     │    └────▲────┘    └──────────┘
│ {name, born} │         │           RATED {rating, timestamp}
└──────┬───────┘         │
       │ ACTED_IN {role} │
       │ DIRECTED        │
       └─────────────────┘
```

### Node labels

| Label | Key properties | Notes |
|---|---|---|
| `Movie` | `title`, `year`, `released`, `plot`, `imdbRating`, `runtime`, `budget`, `revenue`, `languages`, `countries`, `poster`, `imdbId`, `tmdbId`, `plotEmbedding`, `posterEmbedding` | The hub of the graph. Ships with pre-computed plot embeddings (1536-dim, OpenAI) and poster embeddings (512-dim, CLIP) — usable for the hybrid vector+graph stretch goal without generating anything |
| `Person` | `name`, `born`, `bio`, `bioEmbedding` | People also carry the more specific labels below |
| `Actor` | (same as Person) | Sub-label on `Person` nodes that acted in something |
| `Director` | (same as Person) | Sub-label on `Person` nodes that directed something; a person can be both `Actor` and `Director` |
| `Genre` | `name` | ~20 nodes — small lookup-style dimension |
| `User` | `name`, `userId` | Real MovieLens raters, powering collaborative filtering |

Whole dataset: roughly **28.9K nodes and 166K relationships**.

### Relationship types

| Pattern | Properties | Meaning |
|---|---|---|
| `(Person:Actor)-[:ACTED_IN]->(Movie)` | `role` | Cast membership, with the character played |
| `(Person:Director)-[:DIRECTED]->(Movie)` | `role` (rare) | Directing credit |
| `(Movie)-[:IN_GENRE]->(Genre)` | — | Movie categorization (movies usually have several) |
| `(User)-[:RATED]->(Movie)` | `rating` (0.5–5.0), `timestamp` | A real user rating — the raw material for recommendations |

## Modeling Lessons (graph vs. relational)

1. **Relationships are first-class and pre-joined.** In a relational schema,
   `ACTED_IN` would be a join table (`person_id`, `movie_id`, `role`); every
   traversal pays for an index lookup at query time. In the graph, each node
   physically stores pointers to its relationships, so "who acted in this
   movie" is a pointer walk, not a join. This is *index-free adjacency* — the
   core architectural bet of native graph databases.

2. **Relationship properties replace join-table columns.** `role` lives on
   `ACTED_IN`, `rating`/`timestamp` live on `RATED` — data *about the
   connection* belongs on the connection itself.

3. **Multiple labels model roles without inheritance tables.** A person who
   both acts and directs is one node with labels `Person:Actor:Director` —
   no subtype tables, no nullable discriminator columns.

4. **The schema is emergent, not declared.** There is no `CREATE TABLE`;
   labels/properties exist because data uses them, and two `Movie` nodes may
   legitimately carry different property sets (schema-on-read). Constraints
   and indexes can still be added selectively where integrity matters —
   that's part of the M8 AuraDB seeding exercise.

5. **Small "dimension" data stays normalized naturally.** ~20 `Genre` nodes
   shared by thousands of movies — the graph gives you the normalization win
   (one node per genre) *and* cheap traversal to it, with no join penalty.
